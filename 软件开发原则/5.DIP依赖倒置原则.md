# DIP 依赖倒置原则

## 一、基础定义

DIP 全称 **Dependency Inversion Principle（依赖倒置原则）**，是 SOLID 五大设计原则之一，也是实现开闭原则（OCP）的核心手段。它的核心是通过**抽象层**解耦高层模块和低层模块，让两者互不直接绑定。

它有两句经典定义：

1. **高层模块不应该依赖低层模块，二者都应该依赖其抽象。**
2. **抽象不应该依赖细节，细节应该依赖抽象。**

------

## 二、先明确两个基础概念

**1. 高层模块 vs 低层模块**

- **高层模块**：系统的核心业务逻辑、决策层，比如订单结算、支付业务流程，是系统的价值核心，相对稳定，不应该频繁改动。
- **低层模块**：具体的执行、工具、底层操作，比如微信支付实现、数据库增删改、日志打印，是系统的具体实现层，经常变动、扩展。

传统写法的问题：高层直接调用、直接 new 低层对象，高层强依赖低层。低层一改动、一替换，高层就要跟着改。

**2. 抽象 vs 细节**

- **抽象**：接口、抽象类，定义契约和规范，稳定、不轻易改动，是系统的骨架。
- **细节**：具体的实现类、里面的业务代码逻辑，多变、可扩展，是系统的血肉。

------

## 三、“倒置” 到底倒置了什么？

这是最容易误解的点，先明确结论： **倒置的是「依赖关系的方向」，不是「调用关系的方向」。** 调用永远是高层调用低层，这个逻辑不会变；变的是谁依赖谁。

**传统依赖关系（正向）**

高层模块 → 直接依赖低层实现类 比如：订单业务（高层）直接 new 微信支付（低层），订单强依赖微信支付。 → 问题：要换成支付宝支付，必须修改订单业务的代码，高层被低层牵着走。

**倒置后的依赖关系**

高层模块 → 依赖抽象接口 ← 低层实现类

- 高层只依赖抽象接口，不关心具体是谁实现、怎么实现
- 低层实现类必须去实现这个抽象接口，反过来依赖高层定义的契约 → 依赖方向从「高层→低层」变成了「低层→抽象」，所以叫**依赖倒置**。

------

## 四、正反案例对比

**❌ 反面案例：传统写法，违背 DIP**

高层：订单支付业务 低层：微信支付实现

```java
// 低层：具体实现类
public class WechatPayment {
    public void doPay(int amount) {
        System.out.println("微信支付：" + amount + "元");
    }
}

// 高层：订单业务，直接依赖低层具体类
public class OrderService {
    // 高层直接new低层对象，强绑定
    private WechatPayment payment = new WechatPayment();

    public void payOrder(int amount) {
        // 核心业务逻辑...
        payment.doPay(amount); // 直接调用低层方法
    }
}
```

**问题**：

- 高层 `OrderService` 强依赖低层 `WechatPayment`
- 现在要换成支付宝支付，必须修改 `OrderService` 里的代码，把 `WechatPayment` 改成 `AlipayPayment`
- 低层一变，高层就得改，耦合极重，扩展困难，也违背 OCP

**✅ 正面案例：遵循 DIP，依赖抽象**

第一步：定义抽象接口（高层定义的契约，稳定不变）

```java
// 抽象：支付接口，定义支付规范
public interface Payment {
    void pay(int amount);
}
```

第二步：低层实现依赖抽象（细节依赖抽象）

```java
// 低层1：微信支付，实现接口契约
public class WechatPayment implements Payment {
    @Override
    public void pay(int amount) {
        System.out.println("微信支付：" + amount + "元");
    }
}

// 低层2：支付宝支付，实现接口契约
public class AlipayPayment implements Payment {
    @Override
    public void pay(int amount) {
        System.out.println("支付宝支付：" + amount + "元");
    }
}
```

第三步：高层只依赖抽象，不依赖具体实现

```java
// 高层：只依赖Payment接口，不关心具体实现
public class OrderService {
    private Payment payment; // 依赖抽象接口

    // 依赖注入：把具体实现从外部传进来，高层自己不new
    public OrderService(Payment payment) {
        this.payment = payment;
    }

    public void payOrder(int amount) {
        // 核心业务逻辑...
        payment.pay(amount); // 调用抽象方法
    }
}
```

**效果**：

- 高层 `OrderService` 只认 `Payment` 接口，不管你是微信、支付宝还是银行卡
- 新增银行卡支付，只需要加一个 `BankPayment` 实现类，`OrderService` 一行代码都不用改
- 高低层都依赖抽象，完全解耦，同时天然符合 OCP

------

## 五、DIP 的核心价值

1. **解耦**：高层和低层实现没有直接绑定，更换低层实现不影响高层代码
2. **支撑 OCP**：依赖抽象是开闭原则的基础，只有面向抽象编程，才能做到扩展功能不改旧代码
3. **易于测试**：单元测试可以直接 Mock 接口实现，不用依赖真实的低层组件
4. **提升稳定性**：抽象层是稳定的，低层细节的变动不会传导到核心业务层
5. **并行开发**：只要定好接口契约，高层和低层可以并行开发，互不等待

------

## 六、补充说明

1. **和 Spring IOC 的关系** Spring 的 IOC（控制反转）+ DI（依赖注入），就是 DIP 原则在工程上的经典实现。
   - 高层不自己创建低层对象，交给容器注入
   - 组件之间只依赖接口，不依赖具体实现 本质就是把依赖关系的管理交给框架，彻底落地依赖倒置。
2. **常见误区** ❌ 依赖倒置 = 高层调用低层 → 低层调用高层 ✅ 调用方向永远是高层调低层，倒置的是**依赖关系的方向**：低层实现要依赖高层定义的抽象接口。
3. **不是越抽象越好** 不要为了倒置而倒置，稳定的、不会变的低层组件（比如简单工具类），直接依赖也没问题。DIP 主要针对**易变化、可替换**的业务模块。
