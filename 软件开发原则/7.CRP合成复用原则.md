# CRP 合成复用原则

## 一、基础定义与定位

CRP 全称 **Composite Reuse Principle（合成复用原则）**，也叫组合复用原则，是面向对象的经典补充设计原则，核心指导**代码复用方式的选择**。

官方定义：**优先使用组合、聚合的方式来复用代码与功能，而不是通过继承来实现复用。**

通俗理解：想要复用别的类的功能，优先「我持有它，调用它」，而不是「我继承它，变成它」。

------

## 二、先明确：聚合 vs 组合

合成复用里的「合成」，包含**聚合（Aggregation）和组合（Composition）**两种，都是「整体 - 部分」的关联关系，但生命周期绑定强度不同。

| 关系类型 | 关系强度 | 核心语义               | 生命周期                               | 代码表现                   |
| -------- | -------- | ---------------------- | -------------------------------------- | -------------------------- |
| 聚合     | 弱关联   | has-a（拥有一个）      | 部分可以脱离整体独立存在               | 成员变量，对象从外部传入   |
| 组合     | 强关联   | contains-a（包含一个） | 部分和整体同生共死，整体销毁则部分销毁 | 成员变量，内部自己创建对象 |

业务场景举例：

- 聚合：订单和商家，订单删除了，商家依然存在
- 组合：订单和订单项，订单删除了，订单项也随之消失

> 两种都属于合成复用的范畴，核心都是**持有对象、调用方法**，而不是继承父类。

------

## 三、核心本质：用弱耦合复用替代强耦合复用

- **继承复用 = 白盒复用**：父类的内部实现细节，子类完全可见。继承功能的同时，也继承了父类的所有依赖和复杂度，是强耦合。
- **合成复用 = 黑盒复用**：只通过对方的公开接口交互，完全不知道内部实现。耦合度低，各自的内部变化互不影响。

合成复用的核心目标：**降低复用带来的耦合，提升系统的灵活性和可维护性**。

------

## 四、正反案例对比

场景：订单业务和支付业务，都需要用到「短信通知」的功能，怎么复用通知代码。

**❌ 反面案例：继承复用，违背 CRP**

做一个通知基类，业务类通过继承它来复用通知功能：

```java
// 基类：封装通知功能
public class BaseNotifier {
    public void sendSms(String content) {
        System.out.println("发送短信：" + content);
    }
}

// 订单服务：继承基类复用通知
public class OrderService extends BaseNotifier {
    public void createOrder() {
        System.out.println("创建订单");
        sendSms("下单成功"); // 复用父类方法
    }
}

// 支付服务：继承基类复用通知
public class PaymentService extends BaseNotifier {
    public void pay() {
        System.out.println("完成支付");
        sendSms("支付成功"); // 复用父类方法
    }
}
```

**存在的问题**：

1. **强耦合**：`BaseNotifier` 修改方法签名、改动内部逻辑，所有子类都会连锁受影响
2. **单继承限制**：Java 只能单继承，如果还要复用日志校验、权限控制功能，继承无法实现
3. **职责不单一**：业务类同时承担了核心业务 + 通知两个职责，违背 SRP 单一职责
4. **不灵活**：继承是编译期就定死的，运行时无法动态切换通知方式

**✅ 正面案例：组合复用，遵循 CRP**

把通知功能抽成独立的服务类，业务类持有它，通过调用实现复用：

```java
// 独立的通知服务：单一职责，专注通知
public class SmsNotifier {
    public void sendSms(String content) {
        System.out.println("发送短信：" + content);
    }
}

// 订单服务：持有通知对象，组合复用
public class OrderService {
    // 组合：持有通知服务对象
    private SmsNotifier notifier = new SmsNotifier();

    public void createOrder() {
        System.out.println("创建订单");
        notifier.sendSms("下单成功"); // 调用实现复用
    }
}

// 支付服务：同样持有复用
public class PaymentService {
    private SmsNotifier notifier = new SmsNotifier();

    public void pay() {
        System.out.println("完成支付");
        notifier.sendSms("支付成功");
    }
}
```

**扩展升级：新增邮件通知功能** 不需要修改任何原有业务代码，新增邮件通知类，需要的业务替换内部持有对象即可：

```java
// 新增：邮件通知实现
public class MailNotifier {
    public void sendMail(String content) {
        System.out.println("发送邮件：" + content);
    }
}

// 订单服务换成邮件通知，只改内部一行，对外接口完全不变
public class OrderService {
    private MailNotifier notifier = new MailNotifier();
    // 其余代码不动
}
```

如果再配合接口（依赖倒置原则），运行时可以动态切换通知方式，灵活性会更高。

## 五、继承复用 vs 合成复用 对比总结

表格

| 对比维度 | 继承复用                     | 合成复用                           |
| -------- | ---------------------------- | ---------------------------------- |
| 耦合度   | 强耦合，白盒复用             | 弱耦合，黑盒复用                   |
| 灵活性   | 差，编译期定死，运行时不可变 | 好，运行时可动态替换实现           |
| 复用数量 | 单继承，只能复用一个父类     | 支持同时持有多个对象，复用多个功能 |
| 职责划分 | 容易职责混杂，继承链臃肿     | 各自职责单一，边界清晰             |
| 代码量   | 少，直接继承即用             | 稍多，需要额外持有、编排对象       |
| 变更影响 | 父类变更，所有子类连锁影响   | 变更被封装在内部，不影响调用方     |

------

## 六、适用场景

**✅ 优先用合成复用**

- 只是为了复用功能，不存在「is-a（是一个）」的从属关系
- 需要灵活切换复用的实现方式
- 需要同时复用多个不同维度的功能
- 被复用的逻辑可能频繁迭代变更

**✅ 适合用继承**

- 存在明确的「is-a」层级分类关系，且符合里氏替换原则
- 子类和父类是同一事物体系，不是单纯的功能复用
- 父类逻辑非常稳定，几乎不会变更

比如：动物 → 狗 → 泰迪，这种明确的分类层级，适合用继承；而订单 → 通知功能，只是能力复用，适合用组合。

------

## 七、和其他设计原则的关系

1. **支撑 OCP 开闭原则** 组合复用通过新增实现类、替换持有对象来扩展功能，不需要修改原有业务代码，天然符合开闭原则。 继承复用扩展功能往往要修改父类或子类逻辑，更容易违背开闭原则。
2. **配合 SRP 单一职责** 合成复用天然支持单一职责：每个功能类只负责自己的事，业务类只负责编排调用，职责清晰。 继承复用很容易把多个职责揉到同一个继承链里。
3. **补充 DIP 依赖倒置** 组合复用如果面向接口持有对象，就是完整的依赖倒置，耦合度最低、灵活性最高。
4. **规避 LSP 风险** 继承复用很容易出现违背里氏替换原则的情况，组合复用完全没有这个问题，不存在替换契约的风险。
