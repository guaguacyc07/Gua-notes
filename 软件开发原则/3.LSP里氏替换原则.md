# LSP 里氏替换原则

## 一、基础定义与定位

LSP 全称 **Liskov Substitution Principle（里氏替换原则）**，是 SOLID 五大原则的第三个，也是**继承与复用的基石**，更是开闭原则（OCP）能够成立的核心前提。

它的官方定义：**所有引用父类的地方，必须能够透明地使用其子类的对象，并且替换之后不会破坏系统原有的逻辑正确性与行为预期。**

通俗理解： 子类可以扩展父类的功能，但**不能改变父类原有的行为约定**。原来用父类能正常跑的代码，换成任意一个子类对象，代码不用改一行，逻辑也依然正确、结果依然符合预期。

> 注意：它约束的不是「语法上能不能替换」，而是「行为上能不能兼容」。语法能继承、能重写，不代表符合里氏替换原则。

------

## 二、核心本质：行为契约不可违背

LSP 的底层核心是**契约**：父类定义的不仅是方法签名，更是一套行为约定（前置条件、后置条件、不变约束）。子类必须遵守这套契约，只能在契约范围内扩展，不能突破契约。

这也是很多人对继承的最大误区： 

❌ 错误认知：继承就是为了重写父类方法，想怎么改就怎么改 

✅ 正确认知：继承是「是一个」的关系，子类必须首先是一个合格的父类，遵守父类的全部行为约定，再谈扩展。

------

## 三、经典反例：正方形与长方形

这是 LSP 最经典的案例，一眼就能看出问题。

**场景**

按常识理解：正方形是特殊的长方形，所以让 `Square` 继承 `Rectangle`。

```java
// 父类：长方形
public class Rectangle {
    protected double width;
    protected double height;

    public void setWidth(double width) {
        this.width = width;
    }

    public void setHeight(double height) {
        this.height = height;
    }

    public double getArea() {
        return width * height;
    }
}

// 子类：正方形，继承长方形
public class Square extends Rectangle {
    // 重写：设置长的时候，宽也跟着改，保证长宽相等
    @Override
    public void setWidth(double width) {
        super.setWidth(width);
        super.setHeight(width);
    }

    // 重写：设置宽的时候，长也跟着改
    @Override
    public void setHeight(double height) {
        super.setHeight(height);
        super.setWidth(height);
    }
}
```

**问题：违背 LSP**

父类长方形的**行为契约**是：长和宽可以独立变化，互不影响。 子类正方形直接打破了这个契约：设置长会联动宽，设置宽会联动长。

原来针对父类正常的代码，换成子类就会出问题：

```java
// 通用方法：针对长方形设计，设置宽为2、长为5，预期面积10
public void testArea(Rectangle rect) {
    rect.setWidth(2);
    rect.setHeight(5);
    System.out.println(rect.getArea()); // 预期：2*5=10
}

// 用父类：正常
testArea(new Rectangle()); // 输出 10，符合预期

// 换成子类：结果完全错误
testArea(new Square()); // 输出 25，和预期严重不符
```

> 结论：正方形「不是一个」合格的长方形，因为它不遵守长方形的行为契约，继承关系违背 LSP。 正确做法：正方形和长方形应该各自独立，或者共同继承一个更抽象的「图形」父类，各自定义自己的行为。

## 四、业务场景正反案例

沿用之前的支付场景，结合业务逻辑讲解。

**父类契约**

支付接口 / 父类定义行为约定：

- 前置条件：输入金额必须 > 0
- 后置条件：支付成功返回 true，失败返回 false
- 不变量：不会修改订单本身的金额

```java
// 抽象父类：定义支付契约
public abstract class Payment {
    /**
     * 支付
     * @param amount 金额，必须大于0
     * @return 支付是否成功
     */
    public abstract boolean pay(int amount);
}
```

**✅ 符合 LSP 的子类**

```java
// 微信支付：完全遵守契约
public class WechatPayment extends Payment {
    @Override
    public boolean pay(int amount) {
        if (amount <= 0) {
            return false; // 遵守前置条件约定
        }
        System.out.println("微信支付：" + amount + "元");
        return true; // 遵守后置条件约定
    }
}

// 支付宝支付：同样遵守契约
public class AlipayPayment extends Payment {
    @Override
    public boolean pay(int amount) {
        if (amount <= 0) {
            return false;
        }
        System.out.println("支付宝支付：" + amount + "元");
        return true;
    }
}
```

所有接收 `Payment` 父类的地方，换成任意一个子类，逻辑都完全正常，符合 LSP。

**❌ 违背 LSP 的子类**

新增一个「优惠券支付」子类，偷偷改了契约：

```
public class CouponPayment extends Payment {
    private int couponValue = 5; // 优惠券面额

    @Override
    public boolean pay(int amount) {
        // 违背前置条件：金额可以等于0，甚至负数
        int realPay = amount - couponValue;
        if (realPay < 0) {
            System.out.println("优惠券抵扣，无需支付");
            return true;
        }
        System.out.println("优惠券抵扣后支付：" + realPay + "元");
        return true;
    }
}
```

**问题**：

- 父类约定「金额 > 0 才会支付成功」，子类金额为 0 甚至负数也能成功
- 原来依赖父类约定的业务逻辑（比如金额校验、财务对账），换成这个子类就会全部出错
- 表面上继承了父类，实际上打破了行为契约，违背 LSP

## 五、四大判断标准

判断子类是否符合 LSP，看四个契约维度：

表格

| 契约类型     | 规则                               | 说明                                   |
| ------------ | ---------------------------------- | -------------------------------------- |
| **前置条件** | 子类的前置条件**不能比父类更严格** | 父类允许传的参数范围，子类不能缩小范围 |
| **后置条件** | 子类的后置条件**不能比父类更宽松** | 父类保证的返回结果约束，子类不能放宽   |
| **不变量**   | 父类的不变约束，子类**必须保持**   | 父类约定始终成立的规则，子类不能打破   |
| **异常约定** | 子类不能抛出父类没有声明过的异常   | 父类没说会抛的异常，子类不能随便抛     |

简单记忆：子类只能「放宽前置、收紧后置、遵守不变、不抛新异常」。

## 六、常见误区

1. **重写 ≠ 违背 LSP** 不是说重写父类方法就违背 LSP。重写方法但完全遵守父类的行为契约，就符合 LSP。 比如微信支付和支付宝支付，都重写了 pay 方法，但都遵守约定，就是合规的。
2. **子类不能扩展新功能** 完全可以扩展。LSP 只约束「从父类继承来的行为」，子类新增的方法、新增的功能，完全不受限制。
3. **是运行时的问题，不是编译时的** 违背 LSP 的代码，编译完全能通过，语法上没问题。问题出在**运行时逻辑错误、行为不符合预期**，这也是它容易被忽略的原因。

------

## 七、和其他原则的关系

1. **LSP 是 OCP 的基础** 开闭原则的核心是「扩展功能不改旧代码」，靠的就是新增子类替换父类。 如果子类不遵守 LSP，替换之后逻辑出错，那开闭原则就根本无法落地。 可以说：OCP 是目标，LSP 是实现这个目标的基础保障。
2. **和多态的关系** 多态是语法特性，LSP 是设计原则。 多态只保证「语法上能替换」，LSP 保证「行为上替换了也正确」。符合 LSP 的继承，才是正确的多态用法。
3. **和单一职责的关系** 如果父类职责不单一，子类继承的时候就很容易出现「部分职责符合、部分不符合」的情况，间接导致 LSP 被打破。
