# OCP 开闭原则

## 一、基础定义与定位

OCP 全称 **Open-Closed Principle（开闭原则）**，它是面向对象七大设计原则中**最核心、最基础**的原则，其余六个原则（单一职责、里氏替换、接口隔离、依赖倒置、迪米特法则、合成复用）本质上都是围绕开闭原则服务的，最终目标都是让系统更好地满足开闭原则。

它的核心定义只有两句话：

- **对扩展开放（Open for extension）**：系统新增功能、扩展需求时，可以通过新增代码的方式完成。
- **对修改关闭（Closed for modification）**：扩展新功能的过程中，**不修改已经写好、测试通过、稳定运行的原有代码**。

------

## 二、核心判断标准

判断一个设计是否符合 OCP，只看一件事：

> 当你给系统增加新功能的时候，有没有改动之前稳定的旧代码？

- 完全不改动旧代码，只加新代码 → 符合开闭原则
- 需要改动原有逻辑、原有方法才能实现新功能 → 违背开闭原则

只要扩展功能时没修改以前写好的代码，就符合 OCP；修改了之前的程序，设计就是失败的。

------

## 三、为什么必须遵循 OCP？

本质是**控制变更成本、降低系统风险**，对应板书最后一句话的逻辑：

1. **避免全量回归测试** 原有代码是已经测试通过、线上稳定运行的。一旦修改了原有代码，所有依赖这段代码的功能都要全部重新测试，工作量大、周期长，还很容易引入新 bug。
2. **降低维护成本** 每次需求变更都改老代码，代码会越改越乱，逻辑越来越臃肿，最终变成难以维护的 “屎山”。
3. **提升系统稳定性** 稳定的核心逻辑不动，只在外围扩展新功能，核心系统的风险可控，不会因为加一个小功能就影响全链路。

------

## 四、正反案例对比

我们用的「商家订单支付」场景举例

**场景背景**

最初业务只有「微信支付」一种方式，现在要新增「支付宝支付」，后续还要加「银行卡支付」。

**❌ 反面案例：违背 OCP 的写法**

```java
public class PayService {
    // 原有代码：只支持微信支付
    public void pay(String type, int amount) {
        if ("wechat".equals(type)) {
            System.out.println("微信支付：" + amount + "元");
        }
    }
}
```

新增支付宝支付时，必须修改原有 `pay` 方法：

```java
public void pay(String type, int amount) {
    if ("wechat".equals(type)) {
        System.out.println("微信支付：" + amount + "元");
    } 
    // 新增：修改了原有方法代码
    else if ("alipay".equals(type)) {
        System.out.println("支付宝支付：" + amount + "元");
    }
}
```

- 问题：每次加支付方式，都要改动这个核心方法，原有逻辑被反复修改
- 后果：每加一次就要完整测试所有支付方式，改得越多越容易出 bug

**✅ 正面案例：符合 OCP 的写法**

用**抽象接口 + 多个实现类**的方式，把变化隔离出去。

第一步：定义抽象接口（稳定不变的契约）

```java
// 支付接口：稳定，永远不用修改
public interface Payment {
    void pay(int amount);
}
```

第二步：原有功能用实现类完成

```java
// 微信支付实现：原有代码，写完就不动了
public class WechatPayment implements Payment {
    @Override
    public void pay(int amount) {
        System.out.println("微信支付：" + amount + "元");
    }
}
```

第三步：新增功能只加新类，不改旧代码 新增支付宝支付，**只新增一个实现类**，原有接口、微信支付的代码一行都不动：

```java
// 新增：支付宝支付实现
public class AlipayPayment implements Payment {
    @Override
    public void pay(int amount) {
        System.out.println("支付宝支付：" + amount + "元");
    }
}
```

后续再加银行卡支付，依然是新增一个 `BankPayment` 类，所有旧代码完全不用动。

- 好处：原有代码已经测试通过，不需要重新测试；新增功能风险只局限在新代码里
- 完全符合「对扩展开放、对修改关闭」

## 五、OCP 的核心思想

**OCP 的核心思想：抽象构建框架，实现扩展细节**

开闭原则的底层支撑是**面向抽象编程**：

- 抽象（接口、抽象类）是稳定的，是系统的骨架，所以对修改关闭
- 具体的实现类是可变的，是系统的细节，所以对扩展开放

只要系统的抽象层设计得合理，后续所有新增功能都可以通过新增实现类完成，不需要修改上层的核心逻辑，这就是开闭原则的落地方式。

也正是因为这个原因，依赖倒置原则、里氏替换原则、接口隔离原则等，最终都是在帮你设计出稳定、合理的抽象层，最终服务于开闭原则。

------

## 六、补充说明

1. **开闭是相对的，不是绝对的** 完全 100% 不修改任何代码是理想状态，实际开发中做不到绝对开闭。我们追求的是：**核心稳定逻辑不修改，把变化尽量隔离到局部、外围**。 比如配置修改、参数调整不算违反 OCP；核心业务逻辑、公共方法的修改才是。
2. **不是越复杂越好** 如果需求非常简单、几乎不会变更，没必要强行套接口和实现类，过度设计反而增加成本。OCP 针对的是**易变化、可扩展**的业务场景。
3. **和设计模式的关系** 绝大多数设计模式（策略模式、工厂模式、装饰器模式等）的目标，都是实现开闭原则。比如上面的支付例子，本质就是策略模式，最终目的就是在新增策略时不修改原有逻辑。
