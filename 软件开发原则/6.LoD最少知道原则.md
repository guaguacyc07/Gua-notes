# LoD 迪米特法则

## 一、基础定义与定位

LoD 全称 **Law of Demeter（迪米特法则）**，也叫**最少知道原则**，是面向对象的经典补充设计原则（不属于 SOLID 五大原则），核心约束类与类之间的交互深度。

官方定义：一个对象应该对其他对象保持最少的了解，只和自己的「直接朋友」通信，不要和「朋友的朋友」直接交互。

通俗理解：不要跨级调用，不要深挖别人的内部结构。你只需要和直接打交道的类说话，不用知道它内部还有什么部件、怎么实现的。

------

## 二、什么是「直接朋友」

迪米特法则里，只有以下几种对象才算「直接朋友」，可以直接调用：

1. 当前对象自身（`this`）
2. 方法的入参对象
3. 当前对象的成员变量对象
4. 当前对象主动创建出来的对象

> 核心红线：**朋友的朋友，不是朋友**。不要通过一个朋友，去直接调用它内部另一个对象的方法。

------

## 三、核心本质：压缩依赖的深度

迪米特法则的底层逻辑，是**切断依赖的传递链**：

- 如果你跨级调用了朋友的朋友，那么朋友的朋友一改动，你就得跟着改 —— 哪怕你的直接朋友本身没变。
- 遵循迪米特法则，你只依赖直接朋友，直接朋友内部怎么变，只要它对外的接口不变，你就完全不受影响。

本质是用「内部封装转发」换「低耦合」，把跨级的依赖隔离在直接朋友内部。

------

## 四、正反案例对比

沿用商家、地址的业务场景：订单服务需要获取商家的所在城市，用于配送范围判断。

**基础类准备**

```java
// 地址类
public class Address {
    private String province;
    private String city;
    private String detail;

    public String getCity() {
        return city;
    }
    // getter/setter...
}

// 商家类
public class Merchant {
    private String shopName;
    private Address address; // 商家关联地址

    public Address getAddress() {
        return address;
    }
}
```

**❌ 反面案例：违背迪米特法则**

订单服务直接穿透商家，去调用地址的方法：

```java
public class OrderService {
    public String getMerchantCity(Merchant merchant) {
        // 跨级调用：商家的朋友（地址），变成了订单的直接依赖
        return merchant.getAddress().getCity();
    }
}
```

**问题分析**：

1. 订单服务知道了「商家内部有地址对象」「地址有 getCity 方法」这些内部细节
2. 如果以后商家改了结构：比如地址拆分成注册地址、经营地址，或者地址类把 `getCity` 改成了 `getCityName`，订单服务必须跟着改
3. 依赖链：`OrderService → Merchant → Address`，Address 的变更会传导到 OrderService，耦合深、影响面大

**✅ 正面案例：遵循迪米特法则**

商家封装自己的内部细节，对外直接提供城市查询方法；订单只和商家这个直接朋友交互：

```java
// 商家类：封装地址细节，对外只暴露需要的能力
public class Merchant {
    private String shopName;
    private Address address;

    // 转发方法：内部自己去调用地址，对外不暴露地址对象
    public String getCity() {
        return address.getCity();
    }
}

// 订单服务：只和直接朋友 Merchant 打交道
public class OrderService {
    public String getMerchantCity(Merchant merchant) {
        // 只调用直接朋友的方法，完全不知道 Address 类的存在
        return merchant.getCity();
    }
}
```

**效果**：

1. 订单服务完全不知道地址类的存在，只依赖商家
2. 地址类怎么改、商家内部地址结构怎么变，只要商家的 `getCity` 方法不变，订单服务一行都不用改
3. 依赖链只有一层：`OrderService → Merchant`，变更被隔离在商家内部

------

## 五、遵循迪米特法则的好处

1. **降低耦合度**：类之间的依赖只有一层，不会出现依赖传递的雪崩效应
2. **控制变更影响**：内部结构的变更被封装在直接朋友内部，不会向外扩散
3. **代码更健壮**：不依赖内部实现细节，只依赖对外契约，稳定性更高
4. **可读性更好**：调用链路短，逻辑清晰，不用深挖多层结构

------

## 六、常见误区

1. **不是所有链式调用都违反** 比如字符串的链式调用 `str.trim().substring(1)`，这是同一个对象的方法链，返回的还是自身类型，没有引入新的类，不违反迪米特法则。 核心判断标准：有没有引入新的、非直接朋友类的依赖。
2. **不是朋友越少越好** 过度追求最少知道，会产生大量的中间转发类、包装类，反而增加系统复杂度，调用链路变长。 粒度要平衡：稳定的、内部的结构尽量隔离；频繁交互的核心模块，不必强行隔离。
3. **不等于封装** 封装是隐藏类的内部实现，迪米特法则是约束类的依赖深度。封装是对内的，迪米特是对外交互的。 迪米特法则可以理解为「封装原则在交互层面的延伸」。

------

## 七、和其他设计原则的关系

1. **与 SRP 单一职责** 两者都在降低耦合：SRP 是从「职责维度」拆分，减少同一类的变化原因；LoD 是从「依赖深度」压缩，减少跨级的依赖传递。
2. **与 ISP 接口隔离** 两者都在减少不必要的依赖：ISP 是从「接口粒度」控制，不让依赖不需要的方法；LoD 是从「调用深度」控制，不让依赖不需要的内部对象。
3. **最终服务于 OCP 开闭原则** 迪米特法则把变更隔离在类的内部，外部不受影响，天然支持扩展功能不修改外部调用代码，是实现开闭原则的辅助手段。
