# SRP 单一职责原则

## 一、基础定义

SRP 全称 **Single Responsibility Principle（单一职责原则）**，是 SOLID 五大原则的第一个，也是所有设计原则的**基础前提**。

它的官方定义是：**一个类（或方法）应该只有一个引起它变化的原因**。 通俗理解：一个类、一个方法，只负责一件事；只对应一个业务维度的变更，不把不相关的逻辑揉在一起。

> 这里的核心关键词是「变化的原因」，而不是「只做一个动作」。判断标准很简单：你能找到几个独立的理由去修改这个类 / 方法，它就有几个职责。

------

## 二、核心本质：把变化的影响范围锁死

单一职责的底层逻辑，是**控制变更的影响范围**：

- 如果一个类承担了多个不相关的职责，其中一个职责的需求变更，就可能影响到其他职责的逻辑，甚至引入无关的 bug。
- 拆分后每个类只负责一件事，修改 A 功能只会动 A 对应的类，完全不会碰 B 功能的代码，变更风险可控。

这也是为什么说它是所有原则的基础 —— 职责不拆分干净，开闭原则、依赖倒置都无从谈起。

------

## 三、正反案例对比

沿用你熟悉的电商业务场景，分别从**类级别**和**方法级别**举例。

### 1. 类级别：最常见的场景

**❌ 反面案例：违背单一职责**

把订单、支付、通知三个完全独立的业务，塞到同一个类里：

```java
public class OrderService {
    // 创建订单：同时干三件事
    public void createOrder(String goods, int amount) {
        // 1. 订单入库逻辑
        System.out.println("保存订单：" + goods);
        
        // 2. 支付逻辑（第二个职责）
        System.out.println("微信支付：" + amount + "元");
        
        // 3. 短信通知逻辑（第三个职责）
        System.out.println("发送下单成功短信");
    }
}
```

**问题分析**： 这个类有**三个独立的变化原因**：

1. 订单流程变更 → 要改这个类
2. 支付方式换成支付宝 → 要改这个类
3. 通知改成站内信 → 还要改这个类

任何一个需求变更，都要修改同一个类，互相干扰；改支付逻辑甚至可能不小心改坏订单逻辑，风险极高。

**✅ 正面案例：遵循单一职责**

按业务维度拆成三个独立的类，每个类只负责一件事：

```java
// 订单服务：只负责订单生命周期管理
public class OrderService {
    public void createOrder(String goods) {
        System.out.println("保存订单：" + goods);
    }
}

// 支付服务：只负责支付逻辑
public class PaymentService {
    public void pay(int amount) {
        System.out.println("微信支付：" + amount + "元");
    }
}

// 通知服务：只负责消息通知
public class NotifyService {
    public void sendOrderSms() {
        System.out.println("发送下单成功短信");
    }
}
```

**效果**：

- 三个类，各自只有一个变化原因
- 改支付方式只动 `PaymentService`，完全不影响订单和通知
- 每个类逻辑简单，测试、维护都轻松
- 上层业务只需要编排调用这三个服务即可

### **2. 方法级别：同样适用**

单一职责不只是类的原则，方法层面同样适用。

**❌ 反面案例：一个方法干多件事**

```java
// 一个方法：既校验参数、又操作数据库、又组装返回值
public Merchant saveMerchant(String shopName, String phone) {
    // 1. 参数校验
    if (shopName == null || shopName.length() > 50) {
        throw new IllegalArgumentException("店铺名非法");
    }
    if (phone == null || !phone.matches("^1[3-9]\\d{9}$")) {
        throw new IllegalArgumentException("手机号非法");
    }
    
    // 2. 数据库保存
    Merchant merchant = new Merchant();
    merchant.setShopName(shopName);
    merchant.setPhone(phone);
    // 执行insert...
    
    // 3. 组装返回对象
    merchant.setStatus(1);
    return merchant;
}
```

**✅ 正面案例：按职责拆分方法**

```java
public Merchant saveMerchant(String shopName, String phone) {
    // 调用校验方法
    validateParam(shopName, phone);
    // 调用保存方法
    Merchant merchant = doSave(shopName, phone);
    // 调用组装方法
    return wrapResult(merchant);
}

// 只负责参数校验
private void validateParam(String shopName, String phone) {
    if (shopName == null || shopName.length() > 50) {
        throw new IllegalArgumentException("店铺名非法");
    }
    if (phone == null || !phone.matches("^1[3-9]\\d{9}$")) {
        throw new IllegalArgumentException("手机号非法");
    }
}

// 只负责数据库操作
private Merchant doSave(String shopName, String phone) {
    Merchant merchant = new Merchant();
    merchant.setShopName(shopName);
    merchant.setPhone(phone);
    // 执行insert...
    return merchant;
}

// 只负责结果封装
private Merchant wrapResult(Merchant merchant) {
    merchant.setStatus(1);
    return merchant;
}
```

## 四、遵循单一职责的好处

1. **降低代码复杂度** 每个类 / 方法只聚焦一件事，逻辑清晰，可读性高，接手的人一眼就能看懂。
2. **控制变更风险** 一个需求变更，只会修改对应的职责类，影响范围可控，不会牵一发而动全身。
3. **易于单元测试** 每个职责单独写测试用例，场景简单，覆盖全面，不用为了测一个方法准备一堆不相关的条件。
4. **降低协作冲突** 多人开发不同功能模块，各自改各自的职责类，不会同时修改同一个文件，减少代码冲突。

------

## 五、常见误区

1. **不是拆分越细越好** 单一职责不是追求极致拆分，过度拆分会导致类的数量爆炸，调用链路变长，反而增加系统复杂度。 粒度要根据**业务变化频率**来定：稳定不变的逻辑，职责可以稍宽；频繁迭代的模块，才需要拆得更细。
2. **不是一个类只能有一个方法** 很多人误解成 “一个类只能有一个方法”，这是错的。 比如 `MerchantService` 里有增、删、改、查四个方法，它们都属于「商家基础数据管理」这同一个职责维度，变化原因都是「商家基础数据规则变更」，所以完全符合单一职责。
3. **没有绝对的标准** 职责的划分没有唯一标准答案，取决于业务场景、团队规模、迭代频率。 简单说：当你发现修改一个功能时，会改动到这个类里不相关的代码，就说明该拆分了。

------

## 六、和其他原则的关系

- SRP 是 SOLID 的基础，职责不单一，OCP 开闭原则就很难落地 —— 一个类多个职责，扩展其中一个功能，必然会改动到其他职责的代码。
- 同样，职责混乱的类，耦合必然重，DIP 依赖倒置也无从谈起。
- LSP、ISP，本质上也都是在不同维度上贯彻单一职责的思想。
