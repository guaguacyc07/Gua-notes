# ISP 接口隔离原则

## 一、基础定义与定位

ISP 全称 **Interface Segregation Principle（接口隔离原则）**，是 SOLID 五大原则的第四个，核心针对接口的设计粒度。

官方定义：**客户端不应该依赖它不需要的接口；不应该强迫任何实现类去实现自己用不到的方法。**

通俗理解：接口要做「小而专」的细接口，不要做「大而全」的胖接口。一个接口只定义一组相关的行为，用到什么就依赖什么，不要让实现类和客户端背上一堆无用的方法。

------

## 二、核心本质：隔离不必要的依赖

接口隔离的底层逻辑，是**把接口按职责拆分，让依赖只发生在需要的层面**：

- 如果接口做得太胖，方法太多，只要接口里一个方法变更，所有实现这个接口的类都得跟着改 —— 哪怕绝大多数实现类根本用不到这个方法。
- 拆分后，变更只会影响真正依赖这个接口的类，无关的类完全不受影响。

> 注意和单一职责原则（SRP）的区别：
>
> - SRP 针对**类、方法**，关注的是「职责单一，变化原因唯一」
> - ISP 针对**接口**，关注的是「接口粒度，依赖隔离」 简单说：SRP 管类的内部职责，ISP 管接口的契约边界。

------

## 三、正反案例对比

用「商家管理系统」场景举例，不同角色权限不同。

**❌ 反面案例：胖接口，违背 ISP**

做一个大而全的商家管理接口，把所有操作都塞进去：

```java
// 胖接口：包含增删改查、导出所有功能
public interface MerchantService {
    void addMerchant(Merchant merchant);   // 新增
    void deleteMerchant(int id);            // 删除
    void updateMerchant(Merchant merchant); // 修改
    Merchant getById(int id);               // 单个查询
    List<Merchant> list();                  // 列表查询
    void exportExcel();                     // 导出报表
}
```

现在有两个实现类：

1. **管理员实现类**：拥有全部权限，所有方法都需要实现
2. **普通运营实现类**：只有查询权限，不能增删改，也不能导出

普通运营的实现类就会非常尴尬：

```java
public class MerchantOperatorService implements MerchantService {
    @Override
    public void addMerchant(Merchant merchant) {
        // 根本用不到，被迫空实现
        throw new UnsupportedOperationException("无权限");
    }

    @Override
    public void deleteMerchant(int id) {
        // 根本用不到，被迫空实现
        throw new UnsupportedOperationException("无权限");
    }

    @Override
    public void updateMerchant(Merchant merchant) {
        // 根本用不到，被迫空实现
        throw new UnsupportedOperationException("无权限");
    }

    @Override
    public Merchant getById(int id) {
        // 真正需要的方法
        return null;
    }

    @Override
    public List<Merchant> list() {
        // 真正需要的方法
        return null;
    }

    @Override
    public void exportExcel() {
        // 根本用不到，被迫空实现
        throw new UnsupportedOperationException("无权限");
    }
}
```

**问题**：

1. 实现类被迫实现大量无用方法，代码冗余，充满空实现 / 异常
2. 接口加新方法（比如 `importExcel`），所有实现类都得加，哪怕只用查询的类也要改
3. 客户端依赖了不需要的方法，存在误用风险

**✅ 正面案例：细接口，遵循 ISP**

按职责拆分成三个独立的细接口：

```java
// 读操作接口：只定义查询相关
public interface MerchantReadService {
    Merchant getById(int id);
    List<Merchant> list();
}

// 写操作接口：只定义增删改
public interface MerchantWriteService {
    void addMerchant(Merchant merchant);
    void deleteMerchant(int id);
    void updateMerchant(Merchant merchant);
}

// 导出接口：只定义报表导出
public interface MerchantExportService {
    void exportExcel();
}
```

不同实现类按需实现：

```java
// 普通运营：只实现查询接口，只需要实现2个方法
public class MerchantOperatorService implements MerchantReadService {
    @Override
    public Merchant getById(int id) { return null; }

    @Override
    public List<Merchant> list() { return null; }
}

// 管理员：同时实现读写+导出，按需组合
public class MerchantAdminService implements MerchantReadService, MerchantWriteService, MerchantExportService {
    // 实现所有方法，都是自己需要的
}
```

**效果**：

- 实现类只实现自己需要的方法，没有冗余代码
- 新增导入功能，只加 `MerchantImportService` 接口，管理员实现即可，完全不影响普通运营的代码
- 客户端只依赖自己需要的接口，不会接触到无权限的方法

------

## 四、胖接口的主要危害

1. **代码冗余**：实现类被迫实现大量无用方法，充斥空实现、异常抛出
2. **变更影响大**：接口一个方法变动，所有实现类全部要改，波及范围远大于实际需要
3. **误用风险高**：客户端能看到不需要的方法，容易误调用无权限、未实现的功能
4. **可读性差**：接口方法太多，无法快速看出这个接口的核心职责

------

## 五、常见误区

1. **不是拆分越细越好** ISP 不是追求极致拆分，极端到每个接口只有一个方法，反而会导致接口数量爆炸，调用和组合成本上升。 拆分粒度按**业务职责**来：同一组职责、同一变化原因的方法，放在同一个接口里。
2. **所有接口都要拆是误区** 如果所有实现类都用得到接口的全部方法，业务也很稳定，就没必要强行拆分。 ISP 针对的是「接口能力大于部分使用者需求」的场景。
3. **和单一职责不是一回事** 单一职责是类的设计原则，接口隔离是接口的设计原则。 一个符合 ISP 的接口，天然是职责单一的；但一个职责单一的类，可以同时实现多个细接口。

------

## 六、和其他原则的关系

1. **支撑 OCP 开闭原则** 接口隔离后，新增功能可以通过新增接口 + 新增实现来完成，不需要修改原有接口和实现，天然符合开闭原则。
2. **配合 DIP 依赖倒置** 依赖倒置要求依赖抽象，而依赖的抽象必须是细粒度的接口，才是真正的解耦。 如果依赖的是胖接口，本质上还是强耦合，依赖倒置的价值就大打折扣。
3. **和 LSP 互补** LSP 保证子类能替换父接口，ISP 保证接口本身粒度合适，两者共同保障面向接口编程的正确性。
